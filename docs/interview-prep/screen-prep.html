01 — Orientation

What this job description is actually telling you

Read the bullets as a description of the company's daily problem, not a checklist of technologies. Almost every line points the same direction.

"Data transformation and mapping between different system formats," "integrating with third-party services," "gathering requirements from users," and "comfort working directly with customers" together describe an integrations-heavy product on a small team — something that pulls data out of other people's systems, reshapes it, and puts it somewhere useful. Go on the backend, React on the front, and someone who can sit on a call with a customer and then go fix the thing.

That has three consequences for the screen:

  • The coding problem will be practical, not algorithmic. Expect: call an API, page through it, reshape the payload, handle partial failures. Not: balance a red-black tree. If you get a DSA question at all, it will be easy-to-lower-medium — parsing, hash maps, two pointers.
  • Error handling and messy input are the real test. On an integrations team, the code that matters is the code that survives a vendor sending null where the docs promised a string. Volunteering "what happens if this field is missing?" scores higher than a clever one-liner.
  • They are listening to how you talk. "Strong communication skills and comfort working directly with customers" in a JD means the interviewer is explicitly grading your narration. Silent coding, even correct silent coding, reads as a risk for a customer-facing role.
The one-sentence strategy Be the person who talks through tradeoffs while writing straightforward, defensive, well-named code — and who asks about the edge cases before being asked.
02 — Format

How to drive the 60 minutes

A live-coding screen has a predictable shape. Knowing where you are in it stops you from spending twenty minutes on a detail that carries no points.

MinutesWhat's happeningWhat to do
0–5Intros, "tell me about yourself"Two-minute version, ending on why this role. Don't recite a resume.

The clarifying questions that always apply

  • "What's the expected size — hundreds of records or millions?" (decides in-memory vs streaming)
  • "Can I assume the input is well-formed, or should I validate?" (they'll almost always say validate — and now it's a requirement, not gold-plating)
  • "If one record fails, do we abort the batch or skip and report?" (this is the integrations question, and asking it signals you've done this before)
  • "Is this a library function or an HTTP handler?" (decides error returns vs status codes)

Narration that sounds senior, not nervous

Instead of silence

"I'm going to build the lookup map first so the join is O(n) instead of O(n²) — I'll come back and handle the duplicate-key case once the happy path runs."

"I'm going to leave this as a TODO and say it out loud so you know I see it: this assumes the timestamps are UTC. In real code I'd normalize at the boundary."

"Two options here — fail the whole batch, or collect errors and return partial results. For an integration I'd default to partial results with a per-record error, because one bad vendor row shouldn't block the other 999. Want me to build it that way?"

If you get stuck Say what you know, what you've ruled out, and what you'd try next — then ask for a nudge. "I know I need to dedupe by ID before the join; I'm deciding whether to do it in the same pass or a separate one. Any preference?" Being stuck is normal; being stuck silently is the only version that fails you.
03 — Backend

Go rapid-fire

Short verbal questions used to calibrate depth before or during the coding problem. Answer in two or three sentences, then stop — over-answering reads as uncertainty.

Q

What's the difference between a slice and an array, and where does that bite people?

An array has a fixed length that's part of its type; a slice is a header — pointer, length, capacity — pointing into a backing array. The bite is aliasing: two slices can share one backing array, so writing through one is visible through the other, and append either mutates in place (capacity available) or reallocates (capacity exhausted), which means whether a caller sees your change depends on capacity.

a := []int{1, 2, 3, 4, 5}
b := a[:2]           // len 2, cap 5 — same backing array
b = append(b, 99)    // fits in cap, so it overwrites a[2]
// a is now [1 2 99 4 5]

c := a[:2:2]         // three-index slice caps it: len 2, cap 2
c = append(c, 99)    // must allocate; a is untouched
What they're testingWhether you've been burned by a function that "randomly" mutated its caller's data. Mention slices.Clone or the three-index slice as the fix.
Q

How do you avoid goroutine leaks?

Every goroutine needs a guaranteed exit path. The classic leak is a goroutine blocked forever sending on a channel nobody reads from — typically after the caller returned early on a timeout. Two habits fix nearly all of it: pass a context.Context and select on ctx.Done() in every blocking operation, and give one-shot result channels a buffer of 1 so the sender can always complete even if nobody's listening.

// Leaks if the caller gives up: the goroutine blocks forever on send.
func bad(ctx context.Context) (int, error) {
    ch := make(chan int)          // unbuffered
    go func() { ch <- expensive() }()
    select {
    case v := <-ch: return v, nil
    case <-ctx.Done(): return 0, ctx.Err()   // goroutine stranded
    }
}

// Buffer of 1: the send always completes, the goroutine always exits.
func good(ctx context.Context) (int, error) {
    ch := make(chan int, 1)
    go func() { ch <- expensive() }()
    select {
    case v := <-ch: return v, nil
    case <-ctx.Done(): return 0, ctx.Err()
    }
}

Also worth saying: goroutine count is a metric worth graphing — a slow steady climb is a leak, and pprof's goroutine profile shows you exactly which line they're all parked on.

Q

Explain context — what's it for and what are the rules?

It carries cancellation, deadlines, and request-scoped values across API boundaries. When a request is cancelled — client hung up, timeout fired — the cancellation propagates down the whole tree of derived contexts, so the DB query, the outbound HTTP call, and the goroutines all stop instead of doing work nobody wants.

  • First parameter, always named ctx. Never store it in a struct.
  • Always defer cancel() after WithCancel/WithTimeout — not calling it leaks the timer and the parent's child list.
  • context.Value is for request-scoped metadata (request ID, auth subject, trace span), not for passing dependencies. Use a typed unexported key, never a bare string.
  • Cancellation is cooperative: it's a signal, not a kill. Code that never checks it never stops.
The follow-up"Where do you set the timeout?" — per outbound call, derived from the request context, so the total is bounded by the inbound deadline and each dependency gets its own budget.
Q

Channels: buffered vs unbuffered, and what are the closed/nil rules?

Unbuffered is a rendezvous — sender and receiver both block until the handoff happens, so it doubles as synchronization. Buffered decouples them up to the buffer size, which is what you want for a work queue or a fan-in where a little burst absorption helps.

Operationnil channelclosed channel
ReceiveBlocks foreverReturns zero value immediately; v, ok := <-ch gives ok == false
SendBlocks foreverPanics
ClosePanicsPanics (double close)

Convention: the sender closes, never the receiver, and never close from multiple goroutines. With multiple senders, close a separate done channel or use a WaitGroup plus one goroutine that closes after wg.Wait(). A nil channel in a select is genuinely useful — it disables that case, which is how you turn off a branch dynamically.

Q

How do you handle and classify errors?

Wrap with %w to preserve the chain and add context at each layer, inspect with errors.Is for sentinels and errors.As for typed errors. The important design decision on an integrations team is classification: the caller needs to know whether to retry.

var ErrNotFound = errors.New("not found")

type RateLimited struct{ RetryAfter time.Duration }
func (e *RateLimited) Error() string { return "rate limited" }

// Caller decides policy from the type, not from string matching.
if errors.Is(err, ErrNotFound) {
    return nil, nil                       // absence isn't a failure here
}
var rl *RateLimited
if errors.As(err, &rl) {
    time.Sleep(rl.RetryAfter)
    return retry()
}
return fmt.Errorf("sync vendor order %s: %w", id, err)

Wrap messages should read as a stack when concatenated: "sync vendor order A1: fetch line items: unexpected status 502". Add the identifier, not the word "error".

The follow-up"When do you panic?" — programmer bugs and impossible states at startup (a bad regex constant, a missing required env var). Never for an expected runtime failure, and never across a package boundary. Recover only at the top of a request handler so one bad request can't take the process down.
Q

Why does a nil pointer in an interface not equal nil?

An interface value is a pair: type and value. Assigning a nil *MyError to an error gives you an interface with a non-nil type and a nil value, so err != nil is true and the caller takes the error branch on a success.

func broken() error {
    var e *MyError = nil   // typed nil
    return e               // interface is (*MyError, nil) — NOT nil
}
// if broken() != nil { ... }  ← this fires

func fixed() error {
    var e *MyError
    if somethingWentWrong { e = &MyError{} }
    if e == nil { return nil }   // return the untyped nil explicitly
    return e
}

Rule of thumb: declare the return as error and return literal nil on the success path, rather than returning a concrete pointer variable.

Q

Mutex or channel?

Mutex for protecting shared state — a cache, a counter, a connection pool. Channels for transferring ownership of data and for coordinating goroutine lifecycles. "Share memory by communicating" is the slogan, but in practice a sync.Mutex around a map is simpler and faster than routing every read through a goroutine, and simpler wins.

Practical notes: sync.RWMutex when reads dominate heavily; sync.Map only for the two cases it's tuned for (write-once-read-many, or disjoint key sets per goroutine) — otherwise a plain map with a mutex benchmarks better. And always run go test -race; the race detector finds in seconds what code review misses for months.

Q

What are the defer gotchas?

  • Arguments are evaluated at defer time, the call happens at return. defer log(time.Since(start)) logs zero; defer func(){ log(time.Since(start)) }() works.
  • Defers run LIFO, and only at function return — not at the end of a loop iteration. Opening files or response bodies in a loop with defer Close() holds every handle until the function ends. Move the body into its own function, or close explicitly.
  • A deferred closure can modify named return values — that's how you convert a panic into an error, or add context on the way out.
func process(ids []string) (err error) {
    defer func() {
        if err != nil { err = fmt.Errorf("process %d ids: %w", len(ids), err) }
    }()
    for _, id := range ids {
        if err := handleOne(id); err != nil { return err }  // shadows; see note
    }
    return nil
}
Say this out loudThe := inside the loop shadows the named return. It still works here because return err assigns to the named value — but shadowing a named return is exactly the kind of subtlety worth flagging rather than leaving for the reviewer.
Q

How do you model "field was absent" vs "field was zero" in JSON?

This is a real integrations question, and it comes up constantly in PATCH endpoints and vendor payloads. A plain int can't distinguish {"count": 0} from {}. Use a pointer, or json.RawMessage, or a small wrapper type.

type PatchUser struct {
    Name  *string `json:"name,omitempty"`   // nil = don't touch
    Email *string `json:"email,omitempty"`  // &"" = explicitly clear it
    Age   *int    `json:"age,omitempty"`
}

func (p PatchUser) apply(u *User) {
    if p.Name != nil { u.Name = *p.Name }
    if p.Age != nil  { u.Age = *p.Age }
}

Related tags worth knowing: json:"-" to drop a field, json:",string" for APIs that send numbers as strings (very common in vendor payloads), and a custom UnmarshalJSON when a vendor sends a field as either a string or an array depending on the day.

Q

What do you get wrong with http.Client in production?

  • Using http.DefaultClient — it has no timeout, so a hung vendor can pin a goroutine forever. Construct one client with an explicit Timeout and a tuned Transport, and reuse it; a fresh client per call defeats connection pooling.
  • Not draining the body. defer resp.Body.Close() isn't enough for keep-alive reuse — the connection only returns to the pool if the body is read to EOF. io.Copy(io.Discard, resp.Body) before close.
  • Leaving MaxIdleConnsPerHost at 2 while hammering one vendor host, which silently serializes your concurrency.
  • Retrying non-idempotent requests without an idempotency key — that's how customers get double-charged.
var client = &http.Client{
    Timeout: 10 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 20,
        IdleConnTimeout:     90 * time.Second,
    },
}
Q

How do you test Go code?

Table-driven tests as the default shape, httptest.Server to stand in for the vendor, interfaces at the boundary so the thing under test takes a dependency I can fake. Names describe behaviour, not the function: TestMapOrder_RejectsZeroQuantity.

func TestMapOrder(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    int64
        wantErr string
    }{
        {"single line", `{"line_items":[{"quantity":2,"unit_price_cents":500}]}`, 1000, ""},
        {"zero quantity", `{"line_items":[{"quantity":0}]}`, 0, "quantity 0"},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := MapOrder([]byte(tt.input), "vendor-x")
            if tt.wantErr != "" {
                if err == nil || !strings.Contains(err.Error(), tt.wantErr) {
                    t.Fatalf("want error containing %q, got %v", tt.wantErr, err)
                }
                return
            }
            if err != nil { t.Fatalf("unexpected error: %v", err) }
            if got.TotalCents != tt.want { t.Errorf("total = %d, want %d", got.TotalCents, tt.want) }
        })
    }
}

Also mention: t.Parallel() where tests are independent, -race in CI, t.Cleanup over defer in helpers, and golden files for big transformation outputs — which is exactly the mapping work in this JD.

Q

How do you shut a Go service down gracefully?

srv := &http.Server{Addr: ":8080", Handler: mux,
    ReadHeaderTimeout: 5 * time.Second}

go func() {
    if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
        log.Fatalf("listen: %v", err)
    }
}()

ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
<-ctx.Done()

shutdownCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
    log.Printf("forced shutdown: %v", err)
}

The point to make out loud: Shutdown stops accepting new connections and waits for in-flight requests, so a deploy doesn't cut a customer's request in half. Background workers need the same treatment — the shutdown context should reach them too, or you'll drop half-processed jobs.

Q

When would you reach for generics?

When the same logic is genuinely identical across types and the alternative is copy-paste or any plus type assertions — container helpers, a concurrency utility like a bounded Map, a generic result cache. Not for business logic, where a concrete type is clearer. maps, slices, and cmp in the standard library cover most of what people used to hand-roll.

04 — Backend

Go live-coding problems

Five problems that cover most of what a Go screen for this role can throw at you. Every solution below compiles and passes go test -race — type them from memory a few times rather than reading them.

1

Fetch N records concurrently, at most K at a time, preserving order

The single most likely Go problem for an integrations team. Phrased as: "here's a list of 500 IDs and an API that rate-limits at 10 concurrent requests — fetch them all."

Talk through the three requirements as you write: bounded concurrency (a semaphore channel), stable output order (write to out[i], don't append), and cancellation (fail fast so 499 doomed requests don't run).

// FetchAll runs fn over every id with at most `limit` in flight, preserves
// input order in the result, and fails fast on the first error.
func FetchAll[T any](ctx context.Context, ids []string, limit int,
    fn func(context.Context, string) (T, error)) ([]T, error) {

    ctx, cancel := context.WithCancel(ctx)
    defer cancel()

    out := make([]T, len(ids))
    sem := make(chan struct{}, limit)
    var wg sync.WaitGroup
    var once sync.Once
    var firstErr error

    for i, id := range ids {
        wg.Add(1)
        go func(i int, id string) {
            defer wg.Done()

            select {
            case sem <- struct{}{}:            // acquire
            case <-ctx.Done():
                return
            }
            defer func() { <-sem }()           // release

            v, err := fn(ctx, id)
            if err != nil {
                once.Do(func() {
                    firstErr = fmt.Errorf("id %s: %w", id, err)
                    cancel()                    // stop the rest
                })
                return
            }
            out[i] = v   // distinct index per goroutine: no lock needed
        }(i, id)
    }
    wg.Wait()
    return out, firstErr
}
Points you score by saying them

• "Each goroutine writes a distinct index, so there's no data race and no mutex — the slice header itself is never mutated."

• "I'm passing i and id as parameters. Go 1.22 made loop variables per-iteration so it's no longer required, but I'd still write it this way in a codebase that might be on an older version."

• "In real code this is golang.org/x/sync/errgroup with g.SetLimit(10) — I'm hand-rolling it because you asked for the mechanism."

Very likely follow-up: "What if I don't want to abort the batch on one failure?" — collect a per-index error slice instead of failing fast, return ([]T, []error) or a slice of result structs, and don't cancel. That's the right default for ingesting vendor data. Have the answer ready; it's the whole point of the question.

2

Retry with exponential backoff, jitter, and no retry on permanent failures

"Integrating with third-party services" in a JD means this problem is on the table. The two things that separate a real answer from a naive one: jitter (so a thousand clients don't retry in lockstep and re-kill the vendor), and classifying errors so you don't burn five attempts on a 422 that will never succeed.

// Permanent marks an error that must not be retried (4xx, validation).
type Permanent struct{ Err error }

func (p *Permanent) Error() string { return p.Err.Error() }
func (p *Permanent) Unwrap() error { return p.Err }

func Retry(ctx context.Context, attempts int, base, max time.Duration,
    fn func(context.Context) error) error {

    var err error
    for i := 0; i < attempts; i++ {
        if err = fn(ctx); err == nil {
            return nil
        }
        var perm *Permanent
        if errors.As(err, &perm) {
            return err                  // never going to succeed
        }
        if i == attempts-1 {
            break
        }

        backoff := base << i            // 1x, 2x, 4x, 8x...
        if backoff > max {
            backoff = max
        }
        sleep := time.Duration(rand.Int63n(int64(backoff) + 1))  // full jitter

        t := time.NewTimer(sleep)
        select {
        case <-ctx.Done():
            t.Stop()
            return ctx.Err()            // never sleep through a cancellation
        case <-t.C:
        }
    }
    return err
}
Say this"I'm sleeping inside a select on ctx.Done() rather than time.Sleep, so a cancelled request doesn't sit in a backoff for thirty seconds. And I'd honour a Retry-After header over my own backoff when the vendor sends one."

Follow-up: "What if the request isn't idempotent?" — then retrying can duplicate a side effect. Send an idempotency key the server dedupes on, or make the retry safe at the data layer with an upsert on a natural key.

3

Rate limiter (token bucket)

Asked either as "limit our outbound calls to the vendor" or "limit inbound requests per API key." Lazy refill on read is the trick worth knowing — no ticker goroutine to leak, and it works for millions of keys.

type TokenBucket struct {
    mu       sync.Mutex
    tokens   float64
    capacity float64          // burst size
    rate     float64          // tokens per second
    last     time.Time
    now      func() time.Time // injectable, so tests don't sleep
}

func NewTokenBucket(rate, capacity float64) *TokenBucket {
    return &TokenBucket{tokens: capacity, capacity: capacity,
        rate: rate, now: time.Now, last: time.Now()}
}

func (b *TokenBucket) Allow() bool {
    b.mu.Lock()
    defer b.mu.Unlock()

    now := b.now()
    b.tokens += now.Sub(b.last).Seconds() * b.rate   // refill for elapsed time
    if b.tokens > b.capacity {
        b.tokens = b.capacity
    }
    b.last = now

    if b.tokens < 1 {
        return false
    }
    b.tokens--
    return true
}
Score the extra point"I've made now a field so the test can advance time instead of sleeping — a rate limiter test that calls time.Sleep is slow and flaky." Then mention golang.org/x/time/rate as what you'd actually import, and that per-key limiters need eviction or the map grows forever.
4

Worker pool over a job channel

The other shape of the same idea: fixed N workers draining one queue. Prefer this when jobs arrive over time (a stream, a queue consumer) rather than from a known slice.

func WorkerPool(ctx context.Context, jobs []int, workers int, do func(int) int) []int {
    in := make(chan int)
    type res struct{ idx, val int }
    outCh := make(chan res)

    var wg sync.WaitGroup
    for w := 0; w < workers; w++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for idx := range in {                  // exits when `in` closes
                select {
                case outCh <- res{idx, do(jobs[idx])}:
                case <-ctx.Done():
                    return
                }
            }
        }()
    }

    go func() {                                     // producer
        defer close(in)
        for i := range jobs {
            select {
            case in <- i:
            case <-ctx.Done():
                return
            }
        }
    }()

    go func() { wg.Wait(); close(outCh) }()         // closer

    out := make([]int, len(jobs))
    for r := range outCh {
        out[r.idx] = r.val
    }
    return out
}

The structural point to narrate: three goroutine roles — producer closes the input, workers exit when input closes, and one closer goroutine waits on the WaitGroup then closes the output so the main range loop terminates. Getting the close ownership right is what the question is really about.

5

An HTTP handler with validation and typed errors

If they ask you to "expose this as an endpoint," this is the shape. Keep transport concerns (status codes, JSON) in the handler and business logic in a service the handler calls — say that out loud, it's the design point.

type APIError struct {
    Status  int    `json:"-"`
    Code    string `json:"code"`
    Message string `json:"message"`
}

func (e *APIError) Error() string { return e.Code + ": " + e.Message }

func handleCreateOrder(store Store, log *slog.Logger) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        ctx := r.Context()

        var req CreateOrderReq
        body := http.MaxBytesReader(w, r.Body, 1<<20)     // cap the body
        if err := json.NewDecoder(body).Decode(&req); err != nil {
            writeErr(w, &APIError{http.StatusBadRequest, "invalid_json",
                "body is not valid JSON"})
            return
        }
        if req.ExternalID == "" || req.Email == "" {
            writeErr(w, &APIError{http.StatusUnprocessableEntity, "missing_field",
                "external_id and email are required"})
            return
        }

        id, err := store.Create(ctx, req)
        if err != nil {
            var apiErr *APIError
            if errors.As(err, &apiErr) {                   // expected failure
                writeErr(w, apiErr)
                return
            }
            log.ErrorContext(ctx, "create order failed",    // unexpected: log it
                "err", err, "external_id", req.ExternalID)
            writeErr(w, &APIError{http.StatusInternalServerError, "internal",
                "unexpected error"})
            return
        }

        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(http.StatusCreated)
        _ = json.NewEncoder(w).Encode(map[string]string{"id": id})
    }
}
Three things to name

• MaxBytesReader — without it an unbounded body is a trivial memory DoS.

• The error split: expected failures map to a status code and a stable machine-readable code; unexpected ones get logged with context and return a generic message, because internal errors must never leak into a response body.

• The closure over dependencies (store, log) instead of package-level globals — that's what makes the handler testable with httptest.

05 — Frontend & Node

TypeScript & async patterns

"Strong understanding of asynchronous programming patterns" is a JD bullet, which means it's a scored question. These are the ones that actually get asked.

Q

What does this print, and why?

console.log("1 sync");
setTimeout(() => console.log("5 macrotask"), 0);
queueMicrotask(() => console.log("3 microtask"));
Promise.resolve().then(() => console.log("4 promise"));
console.log("2 sync");

Output is 1 sync, 2 sync, 3 microtask, 4 promise, 5 macrotask. All synchronous code runs first. Then the entire microtask queue drains — promise callbacks and queueMicrotask, in FIFO order — and only then does the event loop take one macrotask (setTimeout, I/O). Microtasks queued by microtasks run in the same drain, which is why an infinite promise chain can starve the loop entirely.

The follow-up"Where does await fit?" — everything after an await is a microtask continuation. So await-ing an already-resolved promise still yields to the microtask queue; it does not run synchronously.
Q

Promise.all vs allSettled vs race vs any

The gotcha to volunteerPromise.all rejecting does not cancel the other promises — they keep running, and if one of them later rejects with no handler you get an unhandled rejection. Cancellation needs an AbortController; there is no such thing as cancelling a promise.
Q

Write a concurrency limiter for async work

The TypeScript twin of the Go problem. Promise.all(ids.map(fetch)) fires 500 requests at once and gets you rate-limited; this caps it.

export async function mapLimit<T, R>(
  items: T[],
  limit: number,
  fn: (item: T, index: number) => Promise<R>,
): Promise<R[]> {
  const results = new Array<R>(items.length);
  let next = 0;

  // N workers share one cursor; each pulls the next index when it's free.
  const workers = Array.from({ length: Math.min(limit, items.length) }, async () => {
    while (true) {
      const i = next++;
      if (i >= items.length) return;
      results[i] = await fn(items[i], i);
    }
  });

  await Promise.all(workers);
  return results;
}

The insight to narrate: next++ is safe without a lock because JavaScript is single-threaded — no other worker can run between the read and the increment. That's a genuinely good thing to say out loud; it shows you understand why the concurrency model makes this simple.

Variant they'll ask for: "don't let one failure kill the batch." Wrap the await in try/catch and store {status: "fulfilled" | "rejected"} per index — a hand-rolled allSettled with a concurrency cap, which is exactly what a vendor sync needs.

Q

How do you time out and cancel a fetch?

export async function fetchJSON<T>(
  url: string,
  { timeoutMs = 5000, signal }: { timeoutMs?: number; signal?: AbortSignal } = {},
): Promise<T> {
  const timeout = AbortSignal.timeout(timeoutMs);
  // Combine the caller's cancellation with our timeout.
  const combined = signal ? AbortSignal.any([signal, timeout]) : timeout;

  const res = await fetch(url, { signal: combined });
  if (!res.ok) {
    const body = await res.text().catch(() => "");
    throw Object.assign(new Error(`HTTP ${res.status} for ${url}: ${body.slice(0, 200)}`), {
      status: res.status,
    });
  }
  return (await res.json()) as T;
}

Points: fetch only rejects on network failure, so res.ok must be checked explicitly — forgetting that is the single most common async bug in JS codebases. Including the status and a body snippet in the error message is what makes the eventual production incident debuggable. AbortSignal.any composes cancellation sources so a component unmount and a timeout both work.

Q

Consume a paginated API

An async generator is the elegant answer here, and it's the kind of thing that makes an interviewer sit up: the caller iterates records and never thinks about pages, and memory stays flat because you never accumulate the whole set.

type Page<T> = { items: T[]; next_cursor: string | null };

export async function* paginate<T>(
  fetchPage: (cursor?: string) => Promise<Page<T>>,
): AsyncGenerator<T> {
  let cursor: string | undefined;
  do {
    const page = await fetchPage(cursor);
    for (const item of page.items) yield item;
    cursor = page.next_cursor ?? undefined;
  } while (cursor);
}

// Caller doesn't know pages exist:
for await (const order of paginate(getOrdersPage)) {
  await handle(order);
}
Follow-ups worth pre-loading

• "What if the cursor is broken and loops forever?" — cap total pages, and detect a repeated cursor.

• "Offset vs cursor pagination?" — offset is simple but drifts when rows are inserted mid-scan (you skip or duplicate records) and gets slow at high offsets; cursor pagination on a stable sort key is correct and stays fast.

Q

any vs unknown, and where do types actually help?

any switches type checking off and the unsoundness spreads to everything it touches. unknown is the honest top type: you can hold it, but you must narrow before you use it — which is exactly right for a vendor payload.

// A discriminated union makes the impossible states unrepresentable.
type SyncResult =
  | { status: "ok"; id: string; recordsWritten: number }
  | { status: "partial"; id: string; errors: string[] }
  | { status: "failed"; id: string; reason: string };

function describe(r: SyncResult): string {
  switch (r.status) {
    case "ok":      return `${r.recordsWritten} records`;
    case "partial": return `${r.errors.length} problems`;
    case "failed":  return r.reason;
    default: {
      const _exhaustive: never = r;   // compile error if a case is added
      return _exhaustive;
    }
  }
}

The line that lands: "types are a claim about data I control; at the boundary I validate." A as VendorOrder cast on a JSON response is a lie the compiler believes. Parse with a runtime validator (Zod, Valibot, or a hand-written guard) at the edge, and let the inferred type flow inward from there.

Q

Node/backend TS: anything different from the browser?

  • Blocking the loop. One synchronous CPU-heavy call (a big JSON.parse, a sync crypto call, a regex with catastrophic backtracking) stalls every in-flight request. Move it to a worker thread or a queue.
  • Streams and backpressure. For large payloads, pipe rather than buffer — pipeline() handles error propagation and cleanup that a manual .pipe() chain doesn't.
  • Unhandled rejections terminate the process by default in modern Node. Every background promise needs a .catch, even a logging one.
  • Graceful shutdown on SIGTERM: stop accepting, drain in-flight, close the pool — the same discipline as the Go answer.

React

"Proven track record of building responsive, intuitive user interfaces" — so expect either a small component to build live, or pointed questions about re-renders and data fetching.

1

Live problem: a search box that queries an API as you type

The most common React screen exercise, because it hides four real problems: debouncing, request cancellation, out-of-order responses, and the loading/error/empty states people forget.

function useDebounced<T>(value: T, ms = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(t);      // reset the timer on every keystroke
  }, [value, ms]);
  return debounced;
}

function OrderSearch() {
  const [query, setQuery] = useState("");
  const [state, setState] = useState<
    { status: "idle" | "loading" } | { status: "error"; message: string }
    | { status: "done"; orders: Order[] }
  >({ status: "idle" });

  const debouncedQuery = useDebounced(query);

  useEffect(() => {
    if (!debouncedQuery) { setState({ status: "idle" }); return; }

    const controller = new AbortController();
    setState({ status: "loading" });

    fetchJSON<Order[]>(`/api/orders?q=${encodeURIComponent(debouncedQuery)}`, {
      signal: controller.signal,
    })
      .then((orders) => setState({ status: "done", orders }))
      .catch((err) => {
        if (err.name === "AbortError") return;   // superseded, not a failure
        setState({ status: "error", message: err.message });
      });

    return () => controller.abort();   // cancel on new query or unmount
  }, [debouncedQuery]);

  return (
    <div>
      <label htmlFor="q">Search orders</label>
      <input id="q" value={query} onChange={(e) => setQuery(e.target.value)} />

      {state.status === "loading" && <p>Searching…</p>}
      {state.status === "error" && <p role="alert">{state.message}</p>}
      {state.status === "done" && state.orders.length === 0 && <p>No orders match “{debouncedQuery}”.</p>}
      {state.status === "done" && (
        <ul>{state.orders.map((o) => <li key={o.id}>{o.externalId}</li>)}</ul>
      )}
    </div>
  );
}
The four things to say while writing it

• Cleanup solves the race. Without abort(), a slow response for "ab" can land after the fast one for "abcd" and overwrite it. The cleanup function makes the last request the winning one.

• One state object, not four booleans. isLoading + error + data as separate state lets you represent "loading and errored and has data," which is meaningless. A discriminated union makes that impossible.

• Empty is a state. "No results" is different from "haven't searched yet," and users notice.

• A real app uses TanStack Query here — caching, deduping, retries, stale-while-revalidate. I'm hand-rolling it to show the mechanism.

Q

Why do keys matter, and why is the array index a bad one?

Keys tell React which element in the new list corresponds to which in the old one. With index keys, deleting the first item shifts everything: React thinks item 0 changed its content rather than that item 0 was removed, so it reuses the wrong DOM node — and any state living in that node (an input's text, focus, a CSS transition) sticks to the wrong row. Index keys are fine only for a list that is static and never reordered, filtered, or inserted into.

Q

When does useMemo / useCallback / React.memo actually help?

Three cases: an expensive computation you don't want to redo; a value or callback passed to a React.memo child, where a new reference each render defeats the memo; and a dependency of another hook, where an unstable reference causes an effect to re-run in a loop. Everywhere else it's a cost — you pay allocation and comparison for nothing, and the code is harder to read.

Say the diagnosis order: measure with the Profiler first. Most "React is slow" problems turn out to be a big unmemoised list, state living too high in the tree so a keystroke re-renders the page, or a chart library re-mounting — not a missing useCallback. The best fix is usually moving state down to the component that owns it, not memoising the top.

Worth mentioning if you've kept up: the React Compiler automates most of this, which is a reason not to litter a codebase with hand-written memoisation today.

Q

Controlled vs uncontrolled inputs?

Controlled means React state is the source of truth (value + onChange) — needed for validation as you type, formatting, or driving other UI from the input. Uncontrolled leaves the value in the DOM and reads it with a ref on submit — less code, fewer renders, and it's what form libraries lean on. For a big form, uncontrolled with validation on blur/submit is usually the better default.

The bug they may show youAn input that switches from value={undefined} to value={"x"} flips from uncontrolled to controlled and React logs a warning. Fix: initialise to "", never undefined.
Q

How would you make a 10,000-row table usable?

  • Don't render 10,000 rows. Virtualise (TanStack Virtual, react-window) so only the visible window plus a small overscan is in the DOM.
  • Paginate or filter server-side where the data allows — the fastest render is the one you skip.
  • Memoise the row component and keep row props referentially stable, or virtualisation gains get eaten by re-renders.
  • Keep sort/filter state in the URL so a customer can send you the link when they report "the numbers look wrong" — which for a customer-facing role is worth saying explicitly.
Q

What breaks in useEffect?

  • Missing cleanup — subscriptions, timers, and fetches outlive the component. Every effect that starts something must return a function that stops it.
  • Derived state in an effect — useEffect(() => setFullName(first + " " + last)) causes a second render for something that should just be computed during render.
  • Object/array dependencies recreated each render, so the effect runs every time. Depend on primitives, or memoise the object.
  • Strict Mode double-invocation in development is a feature: it runs mount/unmount/mount to surface exactly the missing-cleanup bug above. Don't "fix" it with a ref guard.
07 — Interfaces

REST, gRPC, and webhooks

"Production APIs (REST and/or gRPC)" plus "API optimization techniques" — two bullets, so budget real preparation here.

Q

Design a REST endpoint. What do you get right?

  • Resources are nouns, verbs are methods. POST /orders, GET /orders/{id}, PATCH /orders/{id}. If you're reaching for POST /orders/{id}/doTheThing, either the action is a resource (POST /orders/{id}/cancellations) or the design needs a rethink.
  • Status codes that mean something: 201 with a Location for creation, 202 when the work is queued and the client must poll, 400 for malformed, 401 vs 403 (who are you / you can't), 404 vs 409 (gone / conflicts with current state), 422 for semantically invalid, 429 with Retry-After.
  • A stable error envelope with a machine-readable code, a human message, and a request ID. Customers quote the request ID; that one field turns a support ticket into a log query.
  • Cursor pagination with an opaque cursor, never offset for anything that mutates.
  • Idempotency keys on unsafe operations, so a client retry after a timeout doesn't create a second order.
  • Versioning in the path (/v1/) — simple, cacheable, obvious in logs.
The line to land"Adding a field is backwards compatible; removing one, renaming one, or tightening validation is not. Clients in the wild will parse strictly whatever you told them, so I treat the response shape as a contract with an out-of-band deprecation process."

Q

An endpoint is slow. What do you do?

Answer in order — the order is the answer, because it shows you measure before you optimise.

  1. Measure where the time goes. A trace, or timing spans around each phase. p50 vs p99 matters: a slow p99 with a fine p50 is contention, GC, or a cold cache, not the algorithm.
  2. Look for N+1 first. It's the answer more often than anything else — one query for the list plus one per row. Fix by batching into a single WHERE id = ANY($1) and joining in memory, or a proper JOIN.
  3. Check the query plan. EXPLAIN ANALYZE; a sequential scan on a big table means a missing or unusable index (a function on the column, a type mismatch, or leading-wildcard LIKE).
  4. Reduce what's returned. Pagination, sparse fieldsets, and not serialising a 2 MB blob nobody reads.
  5. Parallelise independent I/O — three vendor calls that don't depend on each other should be concurrent, with a bounded total deadline.
  6. Then cache, with an explicit invalidation story. Caching is the last resort because a cache with no invalidation plan is a correctness bug on a delay.
Q

How do you build a webhook receiver correctly?

A very likely question given the integrations angle, and one where concrete experience shows immediately.

  • Verify the signature before parsing — HMAC over the raw body, constant-time compare, and a timestamp check to stop replays. That means you need the raw bytes, so the body parser must not have already consumed them.
  • Assume at-least-once delivery. Every provider retries, so duplicates are guaranteed. Store the provider's event ID in a table with a unique constraint and treat the insert conflict as "already handled" — that's an idempotency log, and it costs one table.
  • Assume out-of-order delivery. Don't apply a state transition just because it arrived; compare an event timestamp or version against current state and ignore stale ones.
  • Return 2xx fast, do the work async. Persist the raw payload, enqueue, respond. A slow handler causes provider timeouts and a retry storm on top of an already-slow system.
  • Keep the raw payload. When a customer says "the subscription didn't activate," the original body is the only ground truth.
  • Dead-letter what fails repeatedly with enough context to replay it after a fix.
You have this storyYour RevenueCat webhook does exactly this: it rejects unauthorised calls before doing any work, and uses the subscription_events table as an idempotency log so a replayed event can't double-apply an entitlement. Tell it as a story, not a list.
08 — The signature skill

Data transformation & mapping

"Experience with data transformation and mapping between different system formats" is the most specific bullet in the whole JD. If there's one live problem you can predict, it's this one.

The shape: here's a payload in their format, produce a record in ours. What separates a passing answer from a strong one is entirely in the handling of bad data.

// --- Source: the vendor's shape ---
type SrcOrder struct {
    ID     string    `json:"order_id"`
    Buyer  SrcBuyer  `json:"buyer"`
    Items  []SrcItem `json:"line_items"`
    Placed string    `json:"placed_at"`      // RFC3339 string
}

// --- Target: ours ---
type DstOrder struct {
    ExternalID   string    `json:"external_id"`
    CustomerName string    `json:"customer_name"`
    Email        string    `json:"email"`
    TotalCents   int64     `json:"total_cents"`
    Lines        []DstLine `json:"lines"`
    PlacedAt     time.Time `json:"placed_at"`
    Source       string    `json:"source"`
}

// MapOrder converts one vendor order into our shape, collecting every problem
// instead of bailing on the first one — integrations fail in batches.
func MapOrder(raw []byte, source string) (DstOrder, error) {
    var s SrcOrder
    if err := json.Unmarshal(raw, &s); err != nil {
        return DstOrder{}, fmt.Errorf("decode source order: %w", err)
    }

    var problems []string
    if s.ID == "" {
        problems = append(problems, "missing order_id")
    }
    if s.Buyer.Email == "" {
        problems = append(problems, "missing email_address")
    }

    placed, err := time.Parse(time.RFC3339, s.Placed)
    if err != nil {
        problems = append(problems, fmt.Sprintf("bad placed_at %q", s.Placed))
    }

    d := DstOrder{
        ExternalID:   s.ID,
        CustomerName: strings.TrimSpace(s.Buyer.First + " " + s.Buyer.Last),
        Email:        strings.ToLower(strings.TrimSpace(s.Buyer.Email)),
        PlacedAt:     placed.UTC(),
        Source:       source,
        Lines:        make([]DstLine, 0, len(s.Items)),
    }

    for i, it := range s.Items {
        if it.Qty <= 0 {
            problems = append(problems, fmt.Sprintf("line %d: quantity %d", i, it.Qty))
            continue
        }
        amt := it.Cents * int64(it.Qty)     // integer cents; never float money
        d.Lines = append(d.Lines, DstLine{SKU: it.SKU, Quantity: it.Qty, AmountCents: amt})
        d.TotalCents += amt
    }

    if len(problems) > 0 {
        return d, fmt.Errorf("order %s: %s", s.ID, strings.Join(problems, "; "))
    }
    return d, nil
}

The eight things to say while writing a mapper

  1. Money is integer cents. Never a float. Say it before they ask; it's a one-line credibility test.
  2. Timestamps are normalised to UTC at the boundary, and I ask what the vendor sends when it's ambiguous — a naive local timestamp with no zone is a data-corruption bug waiting for a DST change.
  3. Collect problems, don't bail on the first. One error per record beats an operator fixing one field, re-running, and finding the next.
  4. Return the partial record alongside the error so a caller can quarantine it with context instead of losing it.
  5. Normalise on the way in — trim and lowercase emails, canonicalise IDs — so downstream comparisons don't fail on whitespace.
  6. Absent vs zero. A missing quantity and a quantity of 0 are different facts; pointers or a custom unmarshaller preserve that.
  7. Keep the vendor's ID as external_id with a source label, and put a unique constraint on the pair — that's what makes re-running the sync idempotent instead of duplicating everything.
  8. Unknown fields. Ask whether to ignore them (resilient, silently drops new data) or reject (strict, catches vendor changes early). Naming the tradeoff is the point.
Likely extension"Now do a thousand of these." — that's the concurrency problem from section 04 wrapped around this function: bounded parallelism, per-record errors, a summary of {processed, skipped, failed}, and the failures written somewhere replayable. Mention batching the database writes rather than one INSERT per record.
09 — Craft

Debugging across the stack

"Solid debugging skills across the full stack — from backend services to frontend UI." Expect either "walk me through your hardest bug" or a live "here's a bug report, what do you do?"

Q

A customer says "the dashboard shows the wrong total." Where do you start?

The strong answer is a method, not a list of tools. Bisect the pipeline until the layer that's lying is isolated.

  1. Reproduce, and get specific. Which account, which record, what number did they expect versus see, and when. A vague report costs a day; one ID costs ten minutes.
  2. Find the boundary. Open the network tab: is the wrong number already in the API response, or does the response look right and the UI renders it wrong? That single check halves the search space and is where most people skip a step.
  3. If it's the response — replay the request with curl, then run the query directly. Wrong in the DB, or wrong in the code that shaped it?
  4. If the data is wrong in the DB — it went in wrong. Now it's an ingest bug: find the raw payload for that record and re-run the mapper against it.
  5. If it's the UI — stale cache, a rounding or locale format, a race where two responses landed out of order, or state derived from the wrong source.
  6. Write the failing test first, then fix. Otherwise you don't know you fixed it, and it comes back.
  7. Close the loop with the customer in their language: what happened, whether other records are affected, what you changed.
The sentence that makes this answer land"I try to find the first place the data is wrong, not the first place it looks wrong — those are usually different layers."

Q

Tell me about the hardest bug you've fixed.

Use the sync retry loop from Obius — it's a genuinely good story because it's a distributed-systems bug with a customer-visible symptom.

The story, in the order to tell it

Symptom. "Some devices never finished syncing. The client kept pushing the same batch of operations, the server kept responding, and the queue never drained — so the user saw a spinner forever and burned battery on a loop."

Investigation. "The server was returning success at the HTTP level, so the client's error handling never triggered. Once I looked at the per-operation results rather than the response status, the pattern was obvious: a handful of operations were being rejected by a database constraint every single time, and the client's retry logic treated every non-accepted operation as 'try again later.'"

Root cause. "The protocol had two outcomes — accepted or conflicted — and conflict meant retry. But there's a third category: operations that will never succeed, because the payload violates a constraint. Those were being classified as conflicts, so the client retried them forever."

Fix. "I added a third outcome to the sync response — rejected, with a machine-readable code and the underlying database message — and taught the client to drop those operations from the queue and surface them rather than retry. The batch drains, and the failure is visible instead of invisible."

Lesson. "Any retry protocol needs to distinguish transient from permanent failure explicitly, at the protocol level. If the API can't express 'don't try this again,' the client has no choice but to loop."

That lesson is the same one behind the Permanent error type in the retry problem — which means you can connect a live-coding answer to real experience in one sentence. That connection is worth more than either piece alone.

Monitoring, logging, observability

A JD bullet, so expect at least one question. The trap is listing vendor names; the answer is what you'd instrument and why.

Q

What do you instrument in a new service?

The three pillars, and what each is for:

  • Metrics — cheap, aggregated, good for alerting. The RED method per endpoint: Rate, Errors, Duration as a histogram (so you get p50/p95/p99, not a mean that hides everything). Plus the business metrics that actually matter: records synced, sync failures per vendor, queue depth, webhook lag.
  • Logs — structured (Go's slog, or pino in Node), one event per line, with a request ID, user/account ID, and duration. Never a bare log.Println("here"). Errors log once, at the boundary where they're handled — logging at every layer of the wrap chain produces five lines for one failure.
  • Traces — OpenTelemetry spans from the browser through the API to the database and the outbound vendor call. This is the one that answers "the request took 4 seconds, which part?" — and it's the only one that works well across service boundaries.
log.InfoContext(ctx, "vendor sync complete",

Q

What would you alert on?

Symptoms, not causes — page on things a customer would notice. Elevated error rate or latency against an SLO, a sync that hasn't succeeded in longer than its interval, queue depth growing without recovering, webhook processing lag. Not "CPU is at 80%," which is a dashboard fact, not a customer problem.

Every page needs to be actionable and rare. The failure mode to name: alert fatigue — a channel full of warnings nobody reads is worse than no alerting, because it trains the team to ignore the real one. Anything non-actionable becomes a dashboard or a weekly digest.

Q

How do you know an integration is healthy?

A strong, specific answer for this company: per-vendor dashboards showing success rate, latency, and freshness — how long since the last successful sync. Freshness is the metric that catches the silent failure where nothing errors, the job just stopped running. Plus a count of quarantined records by error code, so a vendor changing a field shows up as a spike in one bucket rather than a slow drift nobody notices until a customer complains.

Q

How do you turn vague user feedback into technical work?

  1. Get to the specific instance. "It's slow" becomes "which screen, what were you doing, roughly when" — then find that request in the logs. Users report feelings; logs report facts, and you need both.
  2. Ask what they were trying to accomplish, not what they want built. Feature requests are usually a guess at a solution; the underlying goal is often served better and cheaper by something else.
  3. Play it back. "So when a sync fails you have no way to tell which records didn't make it — is that the painful part, or is it that it fails at all?" Being wrong out loud is the fastest way to get corrected.
  4. Look for the pattern across customers before building for one. Three people describing the same workaround is a roadmap item; one person is a support conversation.
  5. Close the loop. Tell the person what shipped, in their words. It's the cheapest trust you'll ever buy, and it makes the next report more detailed.

If you have a concrete instance — a piece of feedback that changed what you built — use it. Even from a beta tester on your own app: "a tester kept losing track of which of their reusable blocks was linked where, which is why I built the library view" is a real requirements-to-shipped story.

Q

Tell me about a disagreement with a colleague or a customer.

Pick a real technical disagreement, show that you argued from evidence, and — this is the part people miss — show that you committed to the outcome even if you lost. Interviewers are checking for someone who can be overruled without becoming a problem.

Structure: what each side wanted and why they wanted it (steelman them), what evidence you brought, what was decided, what happened, what you'd do differently. Never a story where the other person was simply an idiot.

Q

What's your weakness / what would you do differently?

Name something real and specific, then the correction you've actually made. A working example from a solo-built product: "Building alone, I under-invested in tests early — I leaned on manually exercising the app. It caught up with me on the sync layer, where the failure modes are combinatorial and manual testing simply can't cover them. Now I write the test first for anything with concurrency or state transitions, and I've been deliberate about looking for code review, because a codebase only I have read has blind spots I can't see by definition."

Avoid"I'm a perfectionist," "I work too hard," and anything that's a strength in a costume. Interviewers have heard them and they read as evasion.
Q

Why do you want to work here?

Two sentences of substance beats a paragraph of enthusiasm. Connect one concrete thing about the company to one concrete thing you've done: the integrations problem, the small-team scope, the customer contact. If you can name their product and what it does for whom, you're already ahead of most candidates — look that up the day before.

Your project, mapped to their bullets

Three stories to have loaded and ready

  1. Optimistic concurrency in the sync protocol. Every entity carries a version; the client sends its base version with each operation; the server compares and returns accepted, conflicted (with the server's current state, so the client can merge rather than guess), or rejected. Talk about why version numbers rather than last-write-wins timestamps: clocks on client devices lie, and a version is a fact about the data rather than about a clock.
  2. The idempotent billing webhook. Verify authorization before any work; use the events table as an idempotency log so an at-least-once redelivery can't double-apply an entitlement; state transitions guarded so a stale event can't downgrade a paying customer. This is the single most on-topic story you have for an integrations team — know the details cold.
  3. Streaming with metering. The user gets the model's tokens as they arrive; a tee'd copy of the same stream is parsed for usage and logged after the fact, with the logging call deliberately not awaited on the response path. The point: observability that doesn't tax the hot path.
If they ask "did you write the Go?"Be straight: you've built production services in TypeScript and you're comfortable in Go, and name honestly what you've done in it. Then pivot to the transferable part — concurrency with explicit cancellation, typed errors with retry classification, protocol design — and demonstrate it in the coding round. Interviewers hire for demonstrated judgment plus honest self-assessment; they discount inflated claims heavily, and they will find out.
13 — Your turn

Questions to ask them

Pick three or four. Good ones are specific to what they told you in the JD and reveal that you're evaluating the job, not just hoping for it.

About the work

  • "The JD mentions mapping data between system formats — how many integrations are you running today, and what usually breaks first when you add a new one?"
  • "Where's the Go/TypeScript line drawn? Is Go the services layer with TypeScript at the edges, or is it more mixed than that?"
  • "REST and/or gRPC — which is it in practice, and is that settled or still being argued about?"
  • "When a customer reports that data looks wrong, what does the path from report to fix look like today? How long does it typically take?"

About the team

  • "How much direct customer contact does an engineer actually have — is that support rotation, discovery calls, or sitting in on implementations?"
  • "What does the first ninety days look like? What would I have shipped by then?"
  • "How do you decide what to build — where does a piece of customer feedback go before it becomes work?"
  • "What's the on-call situation, and what wakes people up most often?"

The two that get the most honest answers

  • "What's the part of the codebase everyone agrees needs work but nobody's had time for?"
  • "What separates someone who does well here from someone who struggles?"
Don't lead withComp, remote policy, and vacation in a technical screen. Those are recruiter conversations — ask them, but ask the recruiter.
